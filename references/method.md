# AgentForge 方法框架

AgentForge 把一个模糊的需求或痛点加工成一个经过评估、重设计和验证的 AI 项目规格。

## 1. 痛点深挖

优先确认会改变方案的未知：使用者、触发频率、当前做法、时间成本、错误代价、最终交付、可用输入、风险和人工责任。不要把对话变成一次性问卷；每轮最多追问少量高影响问题。

## 2. 需求体检

采用三问：痛点是否足够硬、是否有真实高频用户、当前 AI 能力是否刚好够到。再分别检查能力、成本和价值边界。

评级：
- A：高频硬痛点、能力基本验证、结果可验收，优先做。
- B：需求明确、能力大体覆盖，但需要真实样本验证。
- C：需求成立，但关键能力或验证性不足，先用 Prompt/Skill/Tool/Workflow。
- D：需求弱、风险不可接受或无真实使用触发，暂缓。

## 3. 结果重定义

用一句话描述：当【目标用户】遇到【高频任务】时，系统接收【输入】，最终交付【可验收结果】，并在【风险节点】由人确认。

## 4. AI 原生重设计

对旧流程逐项判断：删除、合并、并行、后移、保留、人工闸门。不要把传统岗位直接映射为多个 Agent。

## 5. 组件选型

优先级：确定性程序 → Tool → Skill → Workflow → Agent → Human Gate。

- 能用函数解决，不让模型猜。
- 能用规则检查，不让另一个模型凭感觉审核。
- 固定路径优先 Workflow。
- 可复用方法沉淀 Skill。
- 实时读写交给 Tool/API/RAG。
- 只有路径不确定且需要自主判断时才用 Agent。

## 6. 验证设计

在提高自主权之前先回答“它怎么知道自己错了”。验证分为：格式、规则、工具、证据、人工判断。失败时定位具体失败项，局部修复并复验；设置重试上限和停止条件。

## 7. 人机边界

分开三类事件：
- 澄清：缺少会改变结果的信息。
- 审批：超出授权或有外部副作用的动作。
- 质量检查：系统在授权范围内自行修复。

## 8. MVP

MVP 用来验证最危险的假设，不是先做一个功能少的正式产品。优先用真实任务样本验证需求、能力、成本和信任。

## 9. 红队挑战

在进入构建前，至少问一次：不用 AI 是否更便宜；一个 Prompt 是否够用；固定 Workflow 是否足够；模型升级后架构会不会大量报废。

## 10. 交付

形成 One-page Spec，并明确：最终结果、输入、组件、验证、人工闸门、停止条件、最小实验、评测集和下一步。
